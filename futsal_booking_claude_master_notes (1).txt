FUTSAL STADIUM BOOKING APP
MASTER PROJECT NOTES + CLAUDE CODE INSTRUCTIONS
================================================

PROJECT GOAL
------------

Build a production-quality Flutter mobile application for booking futsal football stadiums/courts.

The application has two main roles:

1. CUSTOMER
2. ADMIN

The backend is Firebase.

The application should be designed as a real booking product, not as a simple demo.

The most important technical requirement is preventing double booking and keeping authorization/business rules secure.

The most important UX requirement is making stadium discovery and booking fast, simple, and clear.

11. DOUBLE BOOKING PREVENTION
================================================

THIS IS A CRITICAL REQUIREMENT.

Flutter-side availability checking is NOT enough.

Two users may open the same slot at the same time.

Therefore final booking confirmation must be protected with server-side logic.

Use appropriate Firestore transaction / Cloud Function logic.

Before confirming a booking:

1. Confirm user is authenticated.
2. Confirm user has permission.
3. Confirm stadium exists.
4. Confirm court exists.
5. Confirm court is active.
6. Validate booking date.
7. Validate opening hours.
8. Validate start time.
9. Validate end time.
10. Validate duration.
11. Validate slot is not blocked.
12. Check for overlapping booking.
13. Calculate/validate price on backend.
36. Create booking atomically.
15. Return success or booking conflict.


OVERLAP RULE

Two bookings overlap when:

existingStart < requestedEnd
AND
existingEnd > requestedStart

Cancelled/rejected bookings should normally not block availability.

Confirmed/pending bookings may block availability depending on the business policy.

The final business rule must be explicit in the implementation.

13. MULTI-SHOP / SUPERVISOR / SUPERADMIN SYSTEM
================================================

The application is a multi-shop futsal booking platform.

The platform owner is the SUPERADMIN.

The Superadmin is the platform-level administrator who owns/operates the app and controls which futsal shops are onboarded and listed in the app.

Each futsal shop has its own SHOP ADMIN.

Roles:

- superadmin
- shopAdmin
- customer

ROLE RESPONSIBILITIES
---------------------

SUPERADMIN
----------

The Superadmin represents the platform owner.

Superadmin can:

- Create futsal shops
- Review shop onboarding requests
- Approve shops
- Reject shops
- Activate/deactivate shops
- Suspend shops
- Edit shop information
- Manage all shops
- Assign/create shop admins
- Invite shop admins
- Remove/revoke shop admin access
- Reset/revoke admin access where appropriate
- View all customers
- View all bookings across all shops
- View all stadium/court data across the platform
- View platform-wide revenue/statistics
- View shop-specific revenue/statistics
- View shop performance
- Control whether a shop is visible/listed in the customer app
- Manage platform-level settings
- Manage platform announcements
- Manage platform-wide booking rules where appropriate
- Manage shop onboarding status
- Control collaboration between the platform and participating futsal shops

SUPERADMIN IS THE ONLY PLATFORM-LEVEL ROLE.

SHOP ADMIN
----------

A Shop Admin belongs to one specific futsal shop.

Shop Admin can:

- Manage their assigned shop profile where permitted
- Manage their stadium/venue information
- Manage their courts
- Manage court pricing
- Manage operating hours
- Manage blocked slots
- Manage bookings for their shop
- Confirm/reject/cancel eligible bookings
- Mark bookings completed
- View customers who booked their shop
- View booking history for their shop
- View shop revenue/statistics
- Upload stadium/court images
- Manage shop-specific notifications/settings

Shop Admin MUST NOT:

- access another shop's private management data
- create another shop
- assign themselves Superadmin
- change their own role
- access platform-wide administration
- modify another shop's admin permissions
- access unrelated shops' revenue
- change platform security settings
- change platform-wide configuration unless explicitly authorized

CUSTOMER
--------

Customers can:

- Discover active/listed shops
- Browse stadiums/courts
- Book available slots
- View their own bookings
- Manage their own profile

A Shop Admin can only manage records where:

record.shopId == authenticatedUser.shopId

The Superadmin can access all shops.

Customers can only access customer-safe/public data and their own private booking/profile data.

Use secure Firebase authorization mechanisms, such as custom claims and/or server-controlled role records, together with Firestore Security Rules and Cloud Functions where appropriate.

SECURITY MODEL
--------------

The system is multi-tenant.

36. IMPORTANT MASTER PROMPT ADDITION: SUPERADMIN
================================================

When working on roles and administration, always use this hierarchy:

SUPERADMIN
    |
    +-- Shop A
    |    +-- Shop Admin A
    |    +-- Stadiums / Courts / Bookings
    |
    +-- Shop B
         +-- Shop Admin B
         +-- Stadiums / Courts / Bookings

I am the platform owner and Superadmin.

The business model is that multiple participating futsal shops can join the platform.

The Superadmin controls the relationship between the platform and participating shops.

A Shop Admin controls only their own shop.

The customer sees active/listed shops and books courts from those shops.

Every shop-specific record must carry shopId or otherwise be securely scoped to the shop.

Do not implement this as one global admin role.

The role model must be:

superadmin
shopAdmin
customer

Use secure server-side authorization and Firebase Security Rules.

A Shop Admin must never be able to change their own role to superadmin.

A Shop Admin must never be able to change shopId to another shop.

The Superadmin must be able to onboard a new shop and assign/invite its Shop Admin.

When a shop is suspended or unlisted, customers should no longer be able to create new bookings for that shop, while existing booking handling should follow the defined business rules.

When implementing dashboards:

Superadmin dashboard = platform-wide data.

Shop Admin dashboard = assigned-shop data only.

Customer application = customer-facing marketplace/booking experience.

Do not leak private shop data between shops.

For every new feature, ask:

- Is this platform-level?
- Is this shop-level?
- Is this customer-level?
- What shopId scope applies?
- What Firebase Security Rule is required?
- Does the Superadmin need access?
- Does the Shop Admin need access?
- Can this action affect another shop?

I am the Superadmin/platform owner.
